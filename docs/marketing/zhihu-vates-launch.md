# 41GB 的 80B MoE，8GB 峰值跑起来了：Vates 开源

> 把 512 个专家留在 SSD，重新设计 Apple Silicon 上的 MoE 推理数据路径

文中的性能和内存数据来自项目基准报告。不同设备、SSD、上下文和配置会得到不同结果，各项消融收益也不能直接相加。

---

做这个项目，起点其实是一个很朴素的问题：

**41GB 的模型，真的需要接近 41GB 的可用内存吗？**

Qwen3-Next-80B-A3B 是一个 MoE 模型。它有 512 个专家，但每个 token 在每个 MoE 层只会选中 10 个。既然一次只用其中一小部分，我想试试能不能把专家权重留在 SSD，算到谁时再读谁，而不是启动时全部搬进内存。

最后跑出来的数据是：

```text
Qwen3-Next-80B-A3B 4-bit

完整权重        约 41 GB
                  ↓
         SSD Streaming
                  ↓
运行内存峰值     约 8 GB
生成速度         约 13–15 tok/s

Apple Silicon · MLX
```

![Vates 将约 41GB 权重通过 SSD Streaming 压到约 8GB 运行峰值，并达到约 13–15 tok/s](assets/zhihu/01-vates-memory-wall.png)

项目叫 **Vates**，现在已经开源。

## 从全量加载改成按需调度

Vates 没有改模型结构。主模型照常运行，只把体积最大的专家权重拆成可独立读取的 blob，放在 SSD 上。gate 完成本层路由后，运行时根据专家 ID 去内存池里查；命中了就直接计算，没命中才读盘。

每个专家在磁盘上是一段连续字节，一次 `pread` 就能读完整，不需要运行时再从几个分片里拼权重。这个布局很重要。只有读取粒度缩小到单个专家，缓存和预取才有意义。

第一版做到这里就能跑了，但速度不好看。原因也很直接：生成一个 token 要经过几十层，如果每层都等 SSD，再快的盘也扛不住这种用法。

所以后来大部分时间，其实都花在一件事上：**尽量不让计算等 I/O。**

## 真正难的不是读盘，是把延迟藏起来

这里最关键的一步是跨层预取。

Vates 不是根据“上次用了谁”来猜下一次，也没有额外训练一个预测模型。它直接复用目标层自己的 gate。

模型运行到第 L 层时，本层 attention 已经产生了一个较新的隐藏状态 `x`。Vates 把这个 `x` 提前送进未来第 L+a 层的 gate。此时的 `x` 还不是未来层最终会看到的输入，因此预测不可能完全准确，但 gate 给出的专家排序已经足够用来生成候选集。

当前调度会根据层的位置选择不同的 ahead：前面的层只向前看 1 层，尽量保住预测召回；后面的层向前看 3 层，给 SSD 留出更长的读取窗口。如果一次 MTP 前向包含多个草稿 token，默认会对它们的 gate 分数取 max：只要其中一个 token 强烈需要某个专家，它就进入候选。随后取 24 个候选专家组成“宽集合”，但不会把它们全部塞进内存。提交预取时，C++ 会先过滤目标层已经常驻的专家，再按照 staging budget 截断真正需要读盘的缺口。

```text
第 L 层的较新隐藏状态 x
          │
          ├── 提前经过第 L+a 层的 gate
          │
          └── 得到未来层专家候选集
                         │
                 过滤已常驻专家
                         │
                 C++ 异步 pread
                         │
          第 L+a 层计算前进入侧区 / staging
```

这段预测仍然留在 MLX 的惰性计算图里。主线程不把候选 ID `.tolist()` 到 Python 再发起读盘，而是给 GPU 结果挂一个 C++ 完成回调：gate 计算一结束，回调拿到专家 ID，立刻从对应层的 blob 执行 `pread`。与此同时，模型继续计算中间层。预取真正要利用的就是这段重叠时间。

到了目标层，真实 gate 路由才是最终答案。已经预读并落入侧区的专家直接命中；没预测到或来不及到位的专家仍由 demand 路径读取，不会因为预测失败而算错。非双源路径还会只把“已经读好且真实路由确实用到”的专家 promote 进池，避免假阳性污染常驻区。

预取宽度也不是越大越好。实验里，候选集变宽时，名义 recall 会持续上升，但更多 `pread` 会抢占同一个 I/O 队列，专家反而更晚到达。Vates 因此分别控制“预测宽度”和“实际读取预算”：前者负责别漏掉，后者负责别把 SSD 淹没。项目的 width × budget 扫描记录的也不只是 recall，还包括真实命中率、timing miss、读盘次数和最终 tok/s。

这套机制的本质不是“更准地猜专家”，而是让一个不完美的预测在正确的时间完成：预测早一点、读取少一点，并尽可能把 SSD 延迟藏在中间层计算后面。

![Vates 跨层预取流程：未来层 gate 预测候选、过滤常驻专家并由 C++ 异步读取](assets/zhihu/02-vates-cross-layer-prefetch.png)

Vates 的专家池分成真实区和侧区。真实区放当前计算确定要用的专家，侧区保留预取结果和近期高频专家。命中后直接按槽位做 GPU gather，不再把同一份专家权重从一个缓冲区复制到另一个缓冲区。

侧区最早是一次性的，每步清空。实际跑下来，这会丢掉大量刚用过、很快又会出现的专家。后来改成持久 LFU，只在需要空间时淘汰低频项。对应消融里，命中率从约 0.76 提升到约 0.81；根据侧区容量不同，吞吐提升约 8%–12%。

预取也不是越多越好。读得太少，下一层仍然 miss；读得太多，会把共享 I/O 队列塞满，真正需要的专家反而到得更晚。最终使用的宽度和预算不是拍出来的，而是扫过 recall、实际命中率、磁盘读取次数和 tok/s 后留下来的。

这里还有一个之前低估的问题：Python 自己也会挡路。

早期探针显示，每层同步、主线程落池和状态记账造成的停顿并不小。于是槽状态、LFU 驱逐、按需读取和预取逐步下沉到 C++，由原生路径统一管理。一次对照实验中，这条路径把吞吐从 13.70 提升到 14.80 tok/s，侧区也从双缓冲变成了单缓冲。

到这一步，SSD 提供容量，C++ 负责 I/O 和池状态，MLX 执行计算，Python 不再参与每层的专家搬运。

## 装得下之后，还得让它跑得动

低内存只是前半段。80B 模型如果每秒只能生成零点几个 token，实际还是没法用。

Qwen3-Next 自带 MTP 头，可以先草拟后续 token，再交给主模型批量验证。Vates 在这条路径上做了两个实验：

- 第一候选失败时尝试 top-2 救回，独立实验中位吞吐提升约 10.8%；
- 根据置信度动态缩短草稿，避免为低质量候选加载太多专家，独立实验提升约 5%–6%。

这两个数字来自不同实验，不能相加。投机宽度也不是越大越好，因为一次验证的 token 越多，单层专家并集通常也越大，最后可能把省下来的时间重新花在读盘上。

长上下文还有另一笔内存账：KV cache。Vates 对 12 个全注意力层使用 IsoQuant K4/V3 和 SO(4) 块旋转，测试中的 128k KV 占用从约 3.0 GiB 降到约 0.68 GiB；线性注意力层的递归状态保持不变。

这些路径合在一起后，生产配置在测试设备上能跑到约 13–15 tok/s。我也给它做了一个 Textual TUI，至少不必盯着终端里一行行调试输出聊天。

## 我最担心的不是崩溃，而是读错专家

流式专家池有一类 Bug 很麻烦：程序不崩，速度看起来也正常，但某个槽位里装错了专家。最后只是输出变了几个 token，很容易被当成模型本身的波动。

项目里有几套检查专门处理这个问题：

- 同一提示词使用 greedy 解码，只改变专家池容量，输出 token 必须逐字节一致；
- `DUAL_VERIFY` 和 `STG_VERIFY` 直接核对池槽里的专家字节；
- 记录单次前向的专家并集，确认池容量没有被投机 batch 撑破；
- 对照 Python 和原生路径，检查优化前后是否仍执行同一组专家。

这些检查抓到过一个真实问题：非连续的专家索引被当成连续内存读取。它不会造成崩溃，却会把错误专家装进池里。如果只看“能不能生成”，很难发现。

K=3、top-k=10 的配置下，实测单层最大专家并集是 30，所以生产配置使用 32 个槽。这个数字不是经验值，而是从实际路由里量出来的。

## 仓库里也保留了失败实验

我没有把所有做过的优化都留在生产路径里。

完整树形验证一次展开多条候选，接受率有机会提高，但它也扩大了专家并集。当前配置下，吞吐最后掉到基线的约 0.46 倍。

滑动窗口专家池试图只保留部分层的池，理论上还能继续省内存，实际需要的重载量超过了 SSD 的可用带宽。

事件门控异步 demand 在机制上能工作，端到端却没有净加速，因为真正耗时的 miss I/O 并没有消失。

这些结果都在 `benchmarks/reports/` 里。对系统优化来说，知道哪条路走不通，往往和那几个成功的百分比一样有用。

## 为什么把它开源

Vates 目前包含流式专家池、跨层预测预取、C++ 原生扩展、MTP 自投机、KV 量化、Textual TUI，以及 60 个测试文件。每轮比较重要的性能实验也尽量保留了命令、结果和 GO/NO-GO 结论。

我更想知道这套思路换到不同 Apple Silicon、不同 SSD 和更长上下文之后会怎样，也想看看它能不能被用到其他 MoE 模型上。单机上的一组数字只是开始，数据路径本身才是这个项目值得继续做的部分。
