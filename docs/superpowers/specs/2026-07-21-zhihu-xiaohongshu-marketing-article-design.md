# vates 知乎与小红书营销文章设计

## 目标

围绕“Apple Silicon Mac 以约 8 GB 运行内存运行 80B MoE 模型”建立清晰记忆点，为 vates 获取 GitHub Stars、真实试用用户和技术影响力。

文章分为知乎版和小红书版。两个版本共享同一组事实，但根据平台读者重新组织叙事，不直接压缩或复制。

## 核心传播主张

主标题信息：

> 41 GB 的 80B MoE 模型，不必全部塞进内存；vates 将运行峰值压到约 8 GB，并在 Apple Silicon 上实现约 13–15 tok/s 的生产路径。

通俗解释：

> 让 512 个专家住在 SSD，需要谁时才把谁请进内存，并提前预测下一层会用到谁。

这两个表达分别承担“数据吸引”和“降低理解门槛”的作用。

## 事实边界

文章只使用仓库 README 与基准报告中已有的数据：

- 目标模型为 Qwen3-Next-80B-A3B 4-bit MLX；
- 4-bit 完整权重约 41 GB；
- 流式生产配置运行内存峰值约 8 GB；
- 生产快路径约 13–15 tok/s；
- 128k 上下文 KV 由约 3.0 GiB 压缩至约 0.68 GiB；
- 持久 LFU 命中率由约 0.76 提升至约 0.81；
- C++ 统一池路径由 13.70 提升至 14.80 tok/s；
- MTP top-2 救回独立实验提升约 10.8%；
- 动态深度 MTP 独立实验提升约 5%–6%；
- 峰值内存优化降低约 0.18–0.22 GB。

必须明确：

- 各项优化来自独立实验，收益不能简单相加；
- 性能取决于设备、模型、上下文、SSD 和运行配置；
- “约 8 GB”是项目实测运行峰值，不代表任意 8 GB Mac 都有足够系统余量；
- 项目当前只支持 Apple Silicon 和 MLX；
- 仓库不包含模型权重，用户需要自行准备兼容模型与专家数据；
- 不使用“所有 Mac”“绝对无损”“全球首个”等无法证实的宣传词。

## 知乎版设计

### 定位

面向 AI 开发者和推理系统工程师，用真实问题、技术机制、实验数据和失败经验建立可信度。篇幅约 2500–3500 字。

### 主标题

《41GB 的 80B MoE，8GB 峰值跑起来了：Vates 开源》

副标题为“把 512 个专家留在 SSD，重新设计 Apple Silicon 上的 MoE 推理数据路径”。标题使用“峰值”避免被误解为 8GB Mac，正文首屏立即说明约 8GB 是项目实测运行峰值。

### 文章结构

1. **挑战默认假设**：从“41GB 模型为什么一定需要接近 41GB 可用内存”切入，而不是从项目功能或优化结果切入。
2. **不可能的结果**：首屏直接视觉化 `41GB → SSD Streaming → 约 8GB → 13–15 tok/s`。
3. **重新设计数据路径**：说明 MoE 每步只激活部分专家，并把专家权重变成可独立调度的数据。
4. **技术亮点**：
   - 零拷贝双源专家池；
   - 持久 LFU 侧区；
   - C++ 统一池状态与并行 `pread`；
   - MTP 自投机与动态深度；
   - KV 量化。
5. **正确性工程**：容量不变性、`DUAL_VERIFY`、`STG_VERIFY` 和逐字节验证。
6. **实测结果**：用一张数据卡展示 41 GB、8 GB、13–15 tok/s、0.68 GiB。
7. **聪明方案的失败**：用树形验证、滑动窗口专家池等 NO-GO 结果强化工程实验叙事。
8. **适用人群与限制**：硬件、模型准备、构建门槛及性能差异。
9. **重新定义边界**：以“本地 AI 缺少的可能不是更大内存，而是另一种运行方式”收束，再给出开源地址。

### 语气

- 第一人称黑客实验与开源发布叙事；
- 使用短句、反问和明确判断制造推进感；
- 先解释问题，再引入术语；
- 用“实测”“在当前配置下”“独立实验”限定数据；
- 不写成论文摘要、Benchmark Report 或 README 功能罗列；
- 保留攻击性，但不使用“满血”“无损”“全部攻克”“最强”等超出证据的宣传词。

## 小红书版设计

### 定位

面向普通 AI 用户、Mac 用户和轻度开发者，用结果反差、类比和短段落降低阅读门槛。正文约 600–900 字。

### 标题候选

1. 《Mac 跑 80B 大模型，我把运行内存压到了约 8 GB》
2. 《41 GB 的 80B 模型，为什么运行时只用了约 8 GB？》
3. 《没想到 SSD 也能“喂”大模型：我的 Mac 80B 推理项目开源了》

推荐使用标题 1：结果直接，用户一眼能理解项目价值。

### 正文结构

1. 三行内给出反差：80B、41 GB、约 8 GB；
2. 用“专家住在 SSD、按需上班”解释 MoE 流式推理；
3. 用四个短亮点说明速度、长上下文、交互界面和正确性；
4. 简短说明项目不是一键下载模型，仍需 Apple Silicon、模型文件和构建环境；
5. 展示 TUI 演示和关键数据；
6. 结尾引导搜索 `AMOS144/Vates`、观看演示、Star 和反馈。

### 配图建议

1. 封面：`80B / 41 GB → 约 8 GB` 三段式大字；
2. TUI 演示截图；
3. “512 个专家住在 SSD”示意图；
4. 内存对比数据卡；
5. 13–15 tok/s 吞吐数据卡；
6. KV 3.0 GiB → 0.68 GiB 对比卡；
7. 项目工作原理简图；
8. GitHub 仓库与开源信息页。

图片中的数据必须带“项目实测，因设备与配置而异”脚注。

### 语气

- 每段 1–3 句；
- 少量使用 `💻`、`⚡`、`🧠` 等符号；
- 避免密集术语和夸张感叹号；
- 不使用“保姆级”“封神”“吊打”等低可信表达。

## 转化路径

两个版本统一采用以下行动顺序：

1. 点击演示视频；
2. 访问 `https://github.com/AMOS144/Vates`；
3. 阅读快速开始或运行 `vates --demo`；
4. Star 项目；
5. 通过 Issue 提交设备、体验和问题反馈。

知乎版直接提供完整链接。小红书版使用“搜索 GitHub：`AMOS144/Vates`”，避免正文链接在平台内不可点击。

## 知乎插图设计

制作三张 1600×900 PNG 技术信息图，统一使用深黑蓝背景、青色数据流、紫色强调和少量绿色状态标识。图片使用本地中文字体进行程序化排版，确保数字、中文和技术术语准确，不使用生成式图片中的文字。

1. **首屏数据卡**：展示 `41GB 权重 → SSD Streaming → 约 8GB 峰值 → 13–15 tok/s`，强化文章第一屏的结果反差。
2. **跨层预取流程图**：展示当前层隐藏状态、未来层 gate、24 个候选、常驻过滤、C++ 异步 `pread` 和侧区命中的完整数据流。
3. **实验结果卡**：展示 KV `3.0 GiB → 0.68 GiB`、LFU `0.76 → 0.81`、C++ 统一池 `13.70 → 14.80 tok/s`。

图片保存到 `docs/marketing/assets/zhihu/`，并插入知乎文章对应章节。每张图底部标注“项目实测，结果因设备与配置而异”。

## 小红书成品设计

制作 8 张 1200×1600、3:4 竖版 PNG，延续 Vates 深色技术视觉，并针对手机阅读放大标题与核心数字：

1. `41GB → 约 8GB` 封面；
2. 每次路由只调用 10/512 个专家；
3. 专家常驻 SSD，按需进入双源专家池；
4. 未来层 gate、24 个候选与 C++ 异步 `pread`；
5. 约 8GB 峰值与 13–15 tok/s；
6. 128k KV `3.0 GiB → 0.68 GiB`；
7. 容量不变性、字节真值校验和 NO-GO 实验；
8. Apache-2.0 开源与 GitHub 搜索入口。

图片保存到 `docs/marketing/assets/xiaohongshu/`。另生成 `docs/marketing/xiaohongshu-vates-paste-ready.txt`，只包含可直接发布的标题、正文、标签和置顶评论，不包含 Markdown 辅助章节。
