# 消除每层 host 同步(GPU 侧 slot 重映射)de-risk 结论

日期:2026-06-08
模型:`Qwen3-Next-80B-A3B`(2-bit 专家流式,`RESIDENT_POOL=1`)
机器:32GB 统一内存 macOS
探针:`mlx_streaming/cli/probe_nosync_ceiling.py`(临时 de-risk,出结论后可删)

## 背景:为什么测这个

`FileStreamingMoeBlock.__call__` 每个 MoE 层都 `inds.tolist()` 把路由结果拉回 CPU 去驱动
LRU 池(算 slot、检测 miss)。48 个 MoE 层 = **每 token 48 次强制 GPU→CPU 同步**,打碎
MLX 的异步图(原生全驻一次 host 往返都没有,整张图一路在 GPU 跑完)。本探针测:把 slot
重映射搬到 GPU(`local = slot_table[inds]`,零 host 往返)后,decode 吞吐上界是多少。

## 做法

1. 正常 patch + warm,灌常驻池;
2. 读 `store._resident._slot_of[layer]` 建每层 GPU 查找表(全局 id→slot,-1=不在池);
3. monkeypatch `FileStreamingMoeBlock.__call__` 为纯 GPU 版(无 `.tolist()`/无 Python LRU),计时;
4. 对照正常路径 tok/s,并用正常路径稳态 store 统计看命中率。
   注:nosync 对 miss 做 clamp 不读盘,故其数是「0 同步 + 0 miss I/O」的上界。

## 数据(每 token 一次 `mx.eval`,与原生 generate 同)

| 槽/层 | prompt | 稳态命中率 | normal tps | nosync 上界 tps | 倍数 |
|---:|---|---:|---:|---:|---:|
| 64 | 长(含举例) | 79.0% | 6.5 | 39.7 | 6.1× |
| 64 | 短 | 79.8% | 9.1 | 43.2 | 4.7× |
| 256 | 长 | 93.4% | 11.5 | 38.7 | 3.4× |

## 两个决定性洞察

1. **无同步上界稳定 ~40 tok/s,远超 21 目标。** 且**工作集全驻(0 miss)时,真实现热路径
   就等于 nosync 路径**(无 miss → 无需同步),故 ~40 是全驻时可达的真实上界。

2. **每层 host 同步是主导开销,与命中/miss 无关地每层无条件付。** 命中率 79%→93.4%
   (miss 20%→6.6%),normal 仅 9.1→11.5(+2.4);而把同步整条拿掉直接 ~40。
   **→ normal 的瓶颈不是 miss 的磁盘 I/O,而是每 token×48 层的同步 + Python LRU 记账。**

## 真机落地结果:负面 —— 探针严重高估,端到端零收益(2026-06-08 复测)

GPU 侧 slot 重映射已**完整实现并验证逐 bit 精确**(`acquire_gpu` + 每层 GPU 查找表,
`GPU_REMAP=1` 默认开;67 项单测全绿;真机三组输出与 host 路径逐字一致)。但真机 A/B 显示
**端到端无任何提速**:

| 配置 | 命中率 | f=命中¹⁰ | GPU_REMAP=0 | GPU_REMAP=1 | 峰值内存 |
|---|---|---|---|---|---|
| 短 prompt 256 槽 无 pin | 84.5% | 0.19 | 7.53 | 7.52 | 13.5G |
| 长 prompt 256 槽 无 pin | 86.7% | 0.24 | 9.11 | 9.16 | 13.5G |
| 256 槽 pin128 | 97.1% | 0.74 | 5.08 | 5.08 | 18.9G |

**根因(经两个控制实验定谳,纠正了「同步」「流水线阈值」两版错误推测):
真实瓶颈是 miss 层的磁盘 I/O,而探针把 miss 一律 clamp,等于偷偷跳过了所有读盘。**

实验1 —— 比例扫描(`probe_remap_fraction.py`,256 槽 warm 稳态):把 p 比例的层换成纯 GPU
(clamp miss、**不读盘**),其余走真路径:

| p | GPU 层数 | tps |
|---:|---:|---:|
| 0 | 0 | 11.45 |
| 0.25 | 12 | 21.57 |
| 0.5 | 24 | 29.12 |
| 0.75 | 36 | 33.85 |
| 1.0 | 48 | 39.80 |

实验2 —— 真机计数器(GPU_REMAP=1,86.7% 命中):`gpu_fastpath_frac = 0.485`,即 48.5% 的层
调用真的走了 GPU 快路径,但 `tok_per_s` 仍 8.73,与 GPU_REMAP=0 持平。

**对齐两者即真相**:实验1 里每把一层换成纯 GPU 就提速,根源是该层 **clamp 掉 miss → 跳过磁盘读**;
实验2 里真实现已有 48.5% 层走快路径(这些层快且无盘),但**另外 51.5% 的 miss 层必须读盘**
(精确性要求),这部分磁盘 I/O 才是主导,GPU remap 不能消除。MISS_SYNC 探针 29.59 vs 真机 8.73
的 3.4× 差距,几乎全是探针省掉的读盘开销。

**根本约束**:GPU remap 只能消除"编排/同步"开销,但本机本模型的主导成本是 **miss 层读盘**。要让它
有效,必须把 miss 率压到极低(近全驻),而 80B 近全驻 ~22GB、pin 到 97% 也要 18.9GB,32GB 装不下。
故此优化在本模型+本机**正确但无效**;真正的提速杠杆是降低 miss 率(更小模型 / 更大内存)或加快
读盘(批量/mmap/预取——另一条正交的路)。代码保留(从不更慢、未来可受益),不计入提速。

教训:de-risk 探针必须忠实包含真实现无法省略的成本(此处=读盘);用 clamp 跳过 miss 来测"上界"
会系统性高估。下文为当初被高估的探针记录,保留以溯源反思。

### 读盘成本量化(`probe_io_cost.py`,256 槽,91.25% 命中)

| 指标 | 值 |
|---|---|
| decode | 9.83 tok/s(4.885s / 48 步) |
| **读盘占 decode** | **31.0%**(1.513s) |
| miss/token | 42 次 |
| 单专家平均加载 | 0.75ms(冷 1.03 / 热 0.157) |

- 读盘 31%,**完全消除的理想上界也只有 ~14.2 tok/s(1.45×)**;到 30 还须再砍 69% 的计算/编排。
- 瓶颈非磁盘带宽,而是**每 token 42 次独立 `mx.load` 的调用开销**(热重载仅 0.157ms);working set
  ~13GB 多半已在 OS page cache。可打的方向是**批量加载 / 预开 mmap 减少调用次数**,而非换盘。

### 一个 token 的消融拆解(`probe_token_breakdown.py`,256 槽,91.4% 命中)

tps 阶梯:A 全真 10.88 → 去读盘 27.81 → 去编排 40.28 → 去 matmul 56.72。归因(秒/token 差分):

| 成分 | ms/token | 占比 |
|---|---|---|
| 读盘(含强制 eval 打碎流水线的连带停顿) | 56.0 | 60.9% |
| 注意力+路由 | 17.6 | 19.2% |
| 编排(.tolist/LRU/写槽) | 11.1 | 12.1% |
| MoE matmul | 7.2 | 7.8% |

注:读盘消融占比(60.9%)远大于 `probe_io_cost` 的函数内墙钟(31%),差额=每次 `mx.eval(w)`
强制同步打碎 MLX 异步流水线的连带损失。

### 惰性加载(`_load_one` 去 `mx.eval`):真实但温和 ~6–11%(纠正一次误判)

控制实验(`probe_lazy_load.py`,三窗口 base→lazy→base 各自 reset 统计):

- **首测误判**:base 14.44(命中 96.6%)vs lazy 26.12(命中 100%),误读成 ~1.8–2.4×。
  实为**命中率随池预热爬升**的假象——同在 100% 命中时 base2=28.5 ≥ lazy 26.12。
- **固定命中率干净对照**(64 槽,~74% 命中):base 8.5/8.89 vs lazy 9.43 → **~1.06–1.11×**;
  真机 run_streaming(86.7% 命中)eager 8.72 → lazy 9.45 → 1.08×。`same_token=true`(逐 bit 精确)。
- 结论:惰性加载真实有效但只 ~6–11%(miss 专家是当层 matmul 立刻要用的,无法与计算充分重叠,
  只能藏住一小部分)。已设为默认(`EAGER_EXPERT_LOAD=1` 可回退)。

### 真正的主杠杆 = 命中率(命中→100% 即逼近目标)

| 稳态命中率 | tok/s | 备注 |
|---:|---:|---|
| 74%(64 槽) | ~9 | |
| 96.6%(256 槽预热中) | 14.4 | |
| **100%(256 槽充分预热)** | **28.5** | 13.5GB,几乎够到 30 |

只要工作集真正驻满(命中→100%),256 槽 13.5GB 下稳态即 ~28.5 tok/s。瓶颈既非算子也非编排,
而是**命中率**——而命中率受可行内存约束(80B 在 32GB 上难以让多样化生成的工作集全驻)。
真实可持续吞吐落在 ~14–28,取决于生成话题让专家工作集多窄。

## 关键修正:每层 miss 检查同步不可避免,但代价很小(实测)

初版担心"全命中层也要一次 miss 检查同步(要知道是否读盘),会吃掉收益"。补测 `MISS_SYNC=1`
(GPU remap 路径里每层额外 `mx.eval` 一个 miss 标志,模拟真实现不可避免的那次同步,但**不带**
Python LRU 记账):

| 槽/层 | 命中率 | normal | GPU+每层同步(MISS_SYNC) | GPU 纯上界(无同步) |
|---:|---:|---:|---:|---:|
| 256 | 93.4% | 11.66 | **29.59** | 38.68 |

**结论:每层裸同步只花掉 ~9 tok/s(38.7→29.6);真正主导的可消除开销是 Python LRU 记账
(set/dict/OrderedDict move/`mx.array` 上传),29.6 vs 11.66 = 2.54×。** 即真实现(GPU remap +
每层 miss 同步 + 仅真 miss 时读盘)在 256 槽下应落在 **~25–29 tok/s,逐 bit 精确,单路即超过
MTP 的 24.7**。miss 的磁盘 I/O 不是主导(79%→93% 命中 normal 仅 +2.4),故真实现略低于 29.6
但仍 ≥ 21。

## 决策:GO

- 上界 40 ≫ 21,且同步是可消除的主导项 → 这条路方向正确、收益空间大。
- 但收益 residency-gated:要稳过 21,需把稳态命中率顶到 97%+(加槽 / `store.pin` 钉全局热专家,机制现成)。
- 与"报告旧称 64 槽=95.6%/18 tok/s"不符:本轮三次实测 64 槽命中率均 ~79–80%、normal 6.5–9.1。
  旧 18/95.6% 未能复现(疑为特定短窗/warm 盘/计数口径),后续以本轮 GPU 侧测得的 normal 为基准。

## 真实现要点(下一步)

- `ResidentExpertPool` 维护每层 GPU `slot_of` 表(int32,-1=缺失),`acquire` 命中走 GPU gather、零 host 往返。
- 热路径:`local = slot_of[inds]`;`miss = (local<0)`。**全命中层完全不同步**;有 miss 时才同步处理缺失专家(读盘→写槽→更新表),其余命中专家仍走 GPU remap。
- 必须逐 bit 精确(与当前 stack/池路径数值一致)→ 配单测,跑全绿。
- 叠加 `store.pin` 钉全局热专家把命中率往 97%+ 顶,放大全命中层占比。

## 附:内存改为 grow-on-demand(替代静态 profile,2026-06-08)

用户反馈静态 profile「容易崩 / 不能动态调整」。澄清:实际不会崩(decode 的 k≤预算恒成立,prefill
超容量优雅回退 stack),但静态确实需手动标定、对新 prompt 不自适应。

改为**按需增长**:每层池起步 16 槽,无空闲槽且未到天花板(`cap_for`=profile 上限或全局 capacity)时
按 ~1.5× 增长,到顶才 LRU 淘汰。`cap_for` 由「一次性预分配量」变为「增长天花板」;profile 退化为可选的
更紧上限。

- **实测(256 槽,`EXPERT_POOL_PROFILE=none`,即纯 grow-on-demand,无任何 profile)**:
  `mlx_peak_gb=10.62`、命中率 0.8454、输出正常、无崩溃。即**默认不配置就拿到了原先靠 profile 才有的
  ~10GB**(对比 uniform-256 的 13.5GB)。吞吐 6.71 tok/s,与基线一致(内存优化不碰吞吐)。
- 增长用 `mx.concatenate` 扩容并保留已驻行数据/slot 索引,GPU `slot_table` 因只追加行而保持有效。
  增长只在预热期偶发,稳态零拷贝。
- 单测覆盖:懒分配(不预留满 capacity)、增长保数据与 slot 不变、容量内零淘汰、profile 作天花板、
  GPU remap 仍逐 bit 精确。全套 75 测试绿。
