# FP 噪声地板实测（确定性 delta 的验收基准）

- 日期：2026-07-04
- 分支：`perf/async-demand-offload`
- 任务：Phase 0 · Task 0.2（plan：`docs/superpowers/plans/2026-07-04-cpp-unified-pool-authority.md`）
- 目的：量化「同一配置多次运行时输出 token 的 run-to-run 波动」，得到噪声地板 **N_floor**，作为后续 Phase 2 判定「某个确定性 delta 是否算 bug」的验收线。

---

## 一、结论（TL;DR）

- **N_floor ≠ 0**：真实 80B 模型、当前运行时下，**baseline greedy 的输出 token run-to-run 不是逐位确定的**。GPU 路径存在浮点非确定性。
- **量化的噪声地板（64-token 窗口，MAXTOK=64）**：
  - **确定前缀** = **19 token**：三次运行的前 19 个 token 逐位完全一致。
  - **分歧起点** = 最早在第 20 个 token（0-based index 19）出现单点翻转。
  - **波动量级** = 单点翻转经**自回归放大**后，尾部逐位差异最高达 **45/64 ≈ 70%**。
- **重要推论**：run-to-run 波动是**双峰**的——要么整窗一致（0 位差异），要么一次平局翻转就级联到尾部大面积不同。因此**「尾部 token Hamming 计数」不能当验收阈值**。这恰好从实测角度支持了 plan 采用的正确性口径：**容量不变性 + 字节真值**（整数/字节真值），而非「最终 token 逐位一致」。

---

## 二、判定方法与对比口径

`run_mtp_spec` 会在同一进程内同时跑两条路径：
- **baseline greedy**（非投机，`mtp/generate.py` 的 `_baseline_greedy`，`argmax` 逐 token 解码）；
- **MTP 投机路径**（spec）。

脚本原本只在 JSON 里打印 `exact_match`（spec==baseline）与 `n_mismatch`（spec vs baseline 的差异位数），**不 dump 任一路径的完整 token 序列**，无法直接做 run-to-run 逐位对比。

本任务关心的是**同一路径 run-to-run 的自我一致性**（noise floor），不是 spec-vs-greedy 的差异。为拿到真值，对测量脚本做了**一处 env 门控的小改**（默认关闭，不污染常规输出）：设置 `DUMP_IDS=1` 时，把 baseline greedy 与 spec 的完整 token 序列以 `DUMP_BASE_IDS` / `DUMP_SPEC_IDS` 前缀打进日志。改动见 `mlx_streaming/runtime/run_mtp_spec.py`，随本报告一同提交。

**对比口径**：取三次独立进程运行日志里的 `DUMP_BASE_IDS`（baseline greedy 那条），做两两逐位对比，度量：
- 首次分歧位置（= 最长公共前缀长度）；
- Hamming 差异位数（逐位不同的总数）。


## 五、N_floor 的定义与验收线

### N_floor（噪声地板）

- **token 级 N_floor ≠ 0**（GPU 浮点非确定性下限）。
- 具体量化（本配置 MAXTOK=64、EXPERT_SLOTS=32、K=3）：
  - **确定区 = 前 19 token**（run-to-run 逐位一致的最长公共前缀）；
  - 分歧最早出现在第 20 个 token；
  - 单点翻转经自回归放大，**单窗最大 Hamming 波动 = 45/64（≈70%）**。

### 后续 Phase 2 的验收线（判定「确定性 delta 是否算 bug」）

因为 run-to-run 波动是双峰的（一次 FP 平局翻转即级联到 ~70% 尾部差异），**不能用「最终 token 的 Hamming 计数」做阈值**——它无法把「1 次 FP 噪声翻转」和「真 bug」区分开。据此，验收线定义如下：

1. **稳定前缀内即为 bug**：任何在确定区（本例前 19 token）出现、且 run-to-run **可复现**的 delta，视为高于噪声地板 → **判 bug**。
2. **稳定前缀之后不看 token 身份**：确定区之外的 token 差异落在噪声地板内，**不可**单凭 token 差异判 bug；必须改用**浮点不变量**来判定——即 plan 的正确性口径「**容量不变性 + 字节真值**」：
   - 池容量不变性（每层 resident 槽数不超 cap、不溢出）；
   - 每层 acquire 得到的专家**权重字节真值**（与磁盘原始 blob 逐字节一致）；
   - 路由 top-k 专家 **id 集合**（整数、确定）。
   这些量是 FP-无关的确定量。C++ 统一池实现只要满足这些整数/字节不变量即视为正确；尾部 token 漂移属噪声地板内、不判 bug。
3. **区分「确定性」与「噪声」的操作方法**：对同一 delta，新旧代码各连跑 ≥3 次。若差异**每次都稳定复现**且落在确定区（或违反上述整数/字节不变量）→ 真 bug；若差异只出现在确定区之外且 run-to-run 本身就在变 → 归入 N_floor，不判 bug。
